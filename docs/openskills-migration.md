# Migrating to OpenSkills

The existing Claude/Codex plugins and OpenCode symlinks are independent registrations. Installing with OpenSkills does not remove them. Choose the loader each agent should use to avoid exposing the same skill twice. OpenSkills installs copies: changes in a source checkout do not automatically propagate. Reinstall the complete set after reviewing an update, then run `sync` again.

1. In the consuming project, inspect `.agent/skills/`, `.claude/skills/`, and `AGENTS.md` before installing. Back up any files or customizations you need. OpenSkills `-y` overwrites matching names and `sync -y` changes the skills section of `AGENTS.md`.
2. Install all track-lab skills and sync as shown in the README. A partial installation is unsupported because skills use relative links to siblings. Verify `npx --yes openskills@1.5.0 list` and read representative note and task skills; inspect their referenced files. Start a new agent session if necessary.
3. Only after verification, disable or remove the old registration using the corresponding agent's supported plugin-management commands. For OpenCode symlinks, inspect their targets first and remove only links you know were created by the old setup. Do not remove a skill directory, another checkout's link, or user data blindly. The existing OpenCode sync script creates project or global symlinks and will recreate them if rerun.
4. Keep your existing track vault and configuration. Neither the installation nor `sync` migrates vault content or grants permission to modify it. If rollback is needed, restore the old registration, remove only the OpenSkills copies installed by this migration, and restore the previous `AGENTS.md` content. Check before removing any files that may have been edited since installation.

The project-local `--universal` location is `.agent/skills/`, which is distinct from native OpenCode's `.opencode/skills/` and from Codex plugin directories. Other agents may not automatically discover that directory; they must read the generated `AGENTS.md` and run the stated OpenSkills command. `--global` is deliberately not used here. Never copy private finance skills into a public project or expose private source in a public `AGENTS.md`.

For maintainers: `plugins/task/references/runtime.md` is the canonical task runtime. Its copies inside each task skill are required because OpenSkills installs each skill separately. Update all copies together and run `python3 scripts/test-openskills-layout.py`. Do not replace these copies with symlinks: in OpenSkills 1.5.0 a test install retained an absolute link to the source checkout, which may disappear after installation.

`sync` can include skills visible from the user's global directories as well as the project. Review the generated section before committing or sharing `AGENTS.md`, especially when private skills are installed globally. When testing or publishing a public project, isolate `HOME` and npm's cache as appropriate and confirm the resulting skill list contains no private names or descriptions.

## Updating and removing retired files

OpenSkills 1.5.0 overlays existing directories when reinstalling; it does not delete files removed from a skill or skills removed from the source. A plain reinstall followed by sync can therefore leave obsolete instructions or scripts active. Before an update, back up the installed copies and `AGENTS.md`. Install the reviewed new revision into an empty temporary project with an isolated `HOME`, then compare its skill names and contents with the installed set. Identify retired skill directories and obsolete files, inspect their source metadata and any local edits, and confirm they belong to this installation. Reconcile only those owned paths after preserving needed edits; never delete another package's or an ambiguous path automatically. Then install the reviewed complete set into the target, run sync, and verify that retired names and files are gone. The CLI test demonstrates both the stale-file behavior and cleanup of synthetic, test-owned paths.
