# Clean-room Implement

実装担当が読める情報を先に限定し、その範囲から実装・検証する。
track ノートは必須ではない。task runner から使う場合も、以下をコード探索より先に適用する。

## 1. 参照境界を決める

ユーザーの指定から、再実装する対象と参照元、利用可能な情報を整理する。
指定がなければ、仕様・公開 API の説明・通常の利用で観測できる入出力を使用し、
参照元のソース、逆アセンブル結果、内部設計の解説、実装由来の疑似コードは使用しない。
公開されているコードも参照実装に含める。

組み込み先のコードは、参照実装を含まない接続部分・型・ビルド設定に限って読める。
境界が不明なファイルは、読む前に範囲を特定する。
検索・履歴・差分・テスト・依存パッケージの探索にも同じ境界を適用し、全体検索で禁止資料の内容を流入させない。

着手前に、対象、許可する資料やパス、除外する資料やパスを短く記録する。
対象または境界が特定できなければ、その不足だけを確認してから対象コードに触れる。

## 2. 実装担当を分離する

参照実装やその内部構造を既に読んだ担当は、同じコンテキストで実装を続けない。
「忘れたつもり」や会話の要約は分離にならない。

通常は許可された資料だけで仕様を作る。参照実装の調査が明示的に認められている場合だけ、
仕様を作る担当が参照実装を調査できる。その担当と実装担当は分ける。
実装担当には、許可された仕様、出典、受け入れ条件、参照境界だけを渡す。
元の会話履歴、コード断片、内部アルゴリズムや構造の説明を渡さない。

分離が必要な場合は、履歴を継承しない新しいエージェントまたはセッションを使う。
新しい担当も禁止資料を読まないよう、作業場所と参照範囲を限定する。
分離できない環境では引き継ぎ用の仕様まで作り、実装は未着手として報告する。

## 3. 振る舞いを仕様にする

小さな作業なら一つの短い Markdown ファイルでよい。対象の振る舞いを記述し、参照境界を満たす既存の仕様があれば追記して使う。
以下を実装担当が判断できる形で残す。

- 入力・出力・エラー・境界条件と、対象外の振る舞い。
- 各要件の出典。観測結果には対象バージョン、入力、出力、再現方法を添える。
- 確認済みの事実、推測、未確定事項の区別。
- 受け入れ条件と、それを確かめる具体的な入出力例。

内部構造の模倣を仕様に混ぜない。公開 API の識別子など、互換性に必要な要素は保持する。
不足は許可資料の確認やブラックボックス観測で埋める。
結果を左右する未確定事項はユーザーに確認し、推測で互換性を約束しない。

## 4. 実装と検証

実装担当は、仕様と許可された組み込み先の情報から設計し、既存の標準機能を優先して実装する。
仕様の入出力例と境界条件から実行可能なチェックを作り、プロジェクトで必要な検証も行う。
参照実装のテストコードは、許可された仕様と同一視して読み込まない。

比較実行が許可されているなら、同じ入力に対する外部出力を比較してよい。
不一致は入力・期待結果・実際の結果として返し、内部の原因説明やコードを実装担当へ渡さない。
仕様不足なら出典を付けて仕様を更新してから修正する。

禁止資料を誤って読んだ場合は対象の実装を止め、何が流入したか記録して担当を分離し直す。
完了時は、成果物、使用した資料、検証結果、未確認の互換性、参照境界への逸脱の有無を報告する。
検証した範囲を超える完全互換や、法的な適合性をこの手順だけで保証しない。

## task runner との接続

runner はコード探索前にこのスキルを適用し、実装と検証の結果を受け取った後、
通常のコミット・worklog 更新を続ける。引き継ぎ仕様だけでは実装完了にしない。
