# Track Task Runner

CLI を使う前に[実行環境](../../references/runtime.md)を読む。振り分けは[track-task-triage](../track-task-triage/SKILL.md)、記録は[track-project-intake](../track-project-intake/SKILL.md)に従う。

track ノートの `## TODO` と `## Bug` チェックリストから実装作業を進める。ノート（ユーザーの
track ボールト内）がタスクの源泉であり、コード変更は現在のプロジェクトの作業ディレクトリで
行われる。両者は別の場所であってよい。このスキルは、track CLI（ノートを読み、完了項目を
worklog ノートへ移す）と通常のコード作業（実装・検証・コミット）を組み合わせる。

項目が完了したら、タスクノートから**外へ移す**。日付つき worklog ノート（タスクノートごとに
1日1つ）へ移すことで、タスクノートのチェックリストには未処理の作業だけが残り、worklog ノートは
出荷済みのものの実行ログとなって出典へリンクされる。どちらのノートも**開発者とエージェントの
共有記録**である。チェックリストは未処理のものを示し、worklog は何をどのコミットで行ったかを
示す。開発者が尋ねずに済むように書くこと。

これは**自律的かつ継続的に**実行される。次の手がつけられる項目を選び、端から端まで完了させて
次へ進む。手がつけられる項目がなくなるまで続ける。

## 前提条件

- `track` CLI が `PATH` 上にあり、ユーザーの通常のボールトに対して解決できること。（track の
  ソースリポジトリ内では `go run ./cmd/track` で代用する。）track のコマンドは通常1行の JSON を
  出力する（`export` は Markdown）。stdout をパースし、exit code 1 の `{"error":...}` は失敗として扱うこと。
- ノートが記述するタスクの対象プロジェクトの git ワーキングツリー。

## 1. タスクノートを特定する

- 明示指定: ユーザーがノートを名指しした場合（タイトル / id / パス）、それを解決する。
  ```sh
  track resolve --term "<title>"          # {"found":true,"note_id":N,"path":"…/note/<id>.md"}
  ```
- 自動検出: intake と同じく現在のリポジトリ名をタイトルとして `resolve` し、見つからなければタイトル検索する。候補の本文を読み、対象プロジェクトとの対応を確認する。別プロジェクトのチェックリストを全 vault 検索で自動選択しない。候補が複数ある場合は特定してから実装する。

現在のチェックリスト状態を得るためにノート全体を読む。

```sh
track export --id <note_id>     # full Markdown body to stdout
```

ノートの**タイトル**も控えること。worklog ノートの命名とバックリンク記述に必要になる。
`resolve` はタイトルを返さない。frontmatter（またはノートを見つけた `search` の結果）から読む。

```sh
track export --id <note_id> --frontmatter | sed -n 's/^title: //p'
```

## 2. チェックリストを解析する

`track tasks --id <note_id> --state TODO,DOING --sort priority` を本文と照合する。
対象は `## TODO` / `## Bug` の下、または明示指定されたフラットノートのタスクリストに限定する。
TODO (`[ ]`) は新規着手、DOING (`[/]`) は既存の差分・コミット・担当状況を確認して再開する。
ただしクリーンルーム指定の判定と担当分離（セクション4）は、再開時の差分・コード確認より先に行う。
他者が作業中なら競合させず保留する。WAITING (`[?]`)、DONE (`[x]`)、CANCELLED (`[-]`) は実装しない。
取り残された DONE は review の担当である。コードフェンス内の例は対象にしない。

親子項目は[共通規約](../../references/runtime.md#task-conventions)に従う。
親は集約として残し、着手可能な子から進める。別ノートの子はリンク先を読み、依頼範囲と対象プロジェクトが一致するときだけ処理する。

## 3. 順序を選ぶ

- 依存関係とユーザーが指定した順序を先に守り、期限・優先度を考慮する。同条件なら小さく局所的なものから着手する。
- 難しいという理由だけで保留しない。仕様・承認・外部条件が不足して進められない場合は、その理由を残して次の着手可能な項目へ進む。
- 各項目の後に本文と状態を読み直し、先行作業の完了によって着手可能になった項目も再評価する。

## 4. Per-item loop (autonomous)

選んだ各項目について、次を行う。

ユーザー指示または対象のチェックリスト行に「クリーンルーム実装」「clean-room」や
「参照元のコードを見ずに再実装する」という明示指定があれば、プラン本文やコードを読む前に
[clean-room-implement](../clean-room-implement/SKILL.md) を適用する。単なる仕様からの実装依頼は該当しない。
プラン本文で初めて指定が判明した場合も、その場でこの経路に切り替える。

指定時は runner を調整役とし、仕様担当と、会話履歴を継承しない新しい実装担当を別エージェントとして起動する。
参照境界の決定、仕様の作成・受け渡し、実装・検証は同スキルに従い、以下の1〜3を置き換える。
TODO の着手は runner が手順2の CLI 操作で記録する。
実装担当から成果物と検証結果を受け取り、完了を確認できた場合だけ4へ進む。
担当を分離できない場合は仕様までで止め、セクション6に従って未完了として保留する。

クリーンルーム指定がない場合は1から進む。

1. **理解**する。チェックリストの行がプランノート（`→ [[…]]`）にリンクしているなら、先にそれを
   読む（`track export --title "<plan note title>"`）。その **Approach** と現在のユーザー指示に従う。プランへのリンクだけで承認済みとは見なさず、
   既に得た承認は引き継ぐ。**Steps** を順に実装し、**Risks** セクションの検証を守る。
   そのうえで関連コードを読む。
2. **実装**する。TODO なら、対象行を読み直して `track task set --id <note_id> --line <N> --state DOING --expect TODO` で着手を記録する。周囲のコードの規約に合わせる。
3. **検証**する。プロジェクト自身のルールに従う。標準のテスト・ビルドコマンドを得るため
   適用される `AGENTS.md`（Claude Code では `CLAUDE.md`）と README を読み、実行する（例: テストスイート、型チェック、ビルド）。
   検証が失敗したら項目を完了扱いにしてはならない。
4. **コミット**する。1つのまとまりとして、プロジェクトの git 規約（ブランチ方針、メッセージの
   流儀、必須トレーラー）に従う。メッセージはセクション7に従い、ノート参照なしで自立させる。
   ユーザーが選んだブランチに留まる。デフォルトブランチなら、先にフィーチャーブランチを作る。
   ユーザーが求めない限り push しない。
5. **項目を worklog ノートへ移す**（次セクション）。そこへ追記し、タスクノートから削除する。
   次の項目へ進む。

項目の合間に確認のために立ち止まらず、進み続けること。無人での一括処理が目的である。

## 5. 完了項目を worklog ノートへ移す

実装・検証・コミットが済んだ項目だけを DONE にし、日付つき worklog へ移す。
review から使う場合は、既存の完了証拠を確認し、新しいコミットや完了日は作らない。
worklog は元のタスクノートと同じ vault に、`YYYYMMDD <task note title>` のタイトルで1日1つ作る。

1. 対象行を読み直し、runner の DOING 項目を CLI で DONE にする。既に DONE なら状態を変えず、元の `[done:]` を保つ。
   ```sh
   track task set --id <note_id> --line <N> --state DONE --expect DOING
   ```
   元の行にコミットハッシュと検証結果を短く添える。既存の証拠、リンク、子項目、補足本文は保つ。
   親に未完了の子がある場合は親を移さない。完了した子を移す前に、親へ完了段階と worklog リンクを残す。
2. worklog を冪等に開き、本文を確認する。既存ノートの場合も `## DONE` 見出しがあることを確認し、欠けていれば追加する。
   ```sh
   printf 'from [[<task note title>]]\n\n## DONE\n' \
     | track open --title "<YYYYMMDD> <task note title>" --tag worklog
   ```
3. 現在の対象行番号を取り直し、項目とその配下を CLI で移す。`refile --line` の `--from` に見出しを付けない。
   ```sh
   track refile --from "<task note title>" --line <N> --to "<YYYYMMDD> <task note title>#DONE"
   ```
   `refile` は移動先を書き込み検証してから移動元を更新する。失敗したら自動再試行や元行の削除をせず、両ノートを読み、どこまで保存されたか報告する。再開時も移動先に同じ出典・項目・コミットの記録がないか確認し、重複移動しない。
4. 両ノートを `export` し、項目と補足が worklog にあり、元の項目だけが除かれたことを確認する。直接編集があれば `track reindex` する。
   親は全必須段階と受け入れ条件を検証できた時点で、現在状態を `--expect` に指定して DONE にし、同じ手順で移す。親の進捗は完了段階と残作業の文で残す。

## 6. 難しい項目の保留

保留する項目は未完了のまま残し、`(YYYY-MM-DD: 保留 — <reason>)` を添える。外部条件待ちは CLI で WAITING にし、待ち先を明記する。未完了の項目を DONE にしない。失敗した項目の差分を次の項目のコミットへ混ぜない。

## 7. 外部向けメッセージ: ボールトを知らない読者向け

PR のタイトルと本文、コミットメッセージ、issue など、ボールトの外へ出る文章は、track ボールト
を参照できない読者に向けて書く。GitHub 上では `[[wikilink]]` もノートのタイトルも解決されない。
「Trackノートの2件に対応」のような報告は、何が変わったのか・なぜ変わるのかを読者に一切伝えない。

- 変更そのものを説明する。どんな問題がどこにあり、何がどう変わり、どう検証されたか。ノートの
  チェックリスト行の文言や worklog の概要文をそのまま転記しない。
- ノートでの管理経緯（どのタスクノート由来か、worklog に記録済みか）は本文の骨格にしない。
  載せるなら末尾の補助的な節に分離する。
- コミットメッセージも同様に自立させる。1行目だけで何が変わったか分かるようにする。
- ユーザーへのセッション内報告（次節）はこの制約の外である。ノート参照はそこでは有効に働く。

## 8. 停止して報告する

手がつけられる未チェック項目がなくなったら停止する。簡潔なサマリーを報告する。

- Done: 完了した各項目とそのコミットハッシュ。現在は worklog ノートへ移されている。
- Deferred: スキップした各項目と、難しい・ブロックされていた理由（タスクノートに残っている）。
- コミットが載ったブランチと、worklog ノートのタイトル（`YYYYMMDD <task note title>`）。

## 安全性

- 依頼された実装・テスト・コミットと、対象 vault のタスク/worklog 更新を進める。push、PR、
  リリース、依頼外の削除はユーザーの承認範囲に従う。既に承認された操作を再確認しない。
- 検証が失敗し、すぐに直せないなら、自分の変更だけを戻すか未コミットのまま残して、その項目を
  保留にして報告する。失敗した項目を worklog ノートへ移してはならない。
- runner で実装した項目はコミット確定後、review の既存完了項目は完了証拠を確認した後に移す。
  どちらも移動先への書き込みを検証するまで元の項目を除去しない。失敗した実行で作業を失わないためである。
