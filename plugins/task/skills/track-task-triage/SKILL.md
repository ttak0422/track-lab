# Track Task Triage

CLI を使う前に[実行環境](../../references/runtime.md)を読む。記録の手順は[track-project-intake](../track-project-intake/SKILL.md)、消化の手順は[track-task-runner](../track-task-runner/SKILL.md)に従う。このスキルはその前段の振り分けだけを担い、記録や実装そのものはそちらへ引き渡す。

タスクノート（ユーザーの track ボールト内）が振り分けの対象であり、実装へ引き渡した後のコード変更は、共通方針に従って対象プロジェクトの worktree で行う。両者は別の場所であってよい。

## 使う場面

入ってきた作業依頼が曖昧なまま溜まっているとき、既存のチェックリストが大小混在で手がつけられないとき、1つの大きな項目をどう割るか決めたいときに発動する。典型的な言い回しは「タスクを整理して」「サイズで分けて」「どれからやるべきか決めて」である。

純粋な記録（`track-project-intake`）、チェックリストの一括消化（`track-task-runner`）、調査の書き留め（note プラグインの `track-report`）にはこれを使わない。

## 前提条件

- `track` CLI が `PATH` 上にあり、ユーザーの通常のボールトに対して解決できること。track のソースリポジトリ内では `go run ./cmd/track` で代用する。track のコマンドは通常1行の JSON を出力する（`export` は Markdown）。stdout をパースし、exit code 1 の `{"error":...}` は失敗として扱うこと。
- 振り分け対象のノートが決まっていること。決まっていなければステップ 1 で特定する。

## 1. 集める

対象ノートが名指しされていない場合、まず特定する。プロジェクト作業ならリポジトリ名をタイトルとみなして解決し、見つからなければタイトル検索で範囲を広げる。

```sh
track resolve --term "<project>"
track search --scope title --query "<project>"
```

見つからなければ intake の新規ノート作成手順へ進む。既存項目の振り分けでは元の行を更新し、intake を通して同じ項目を追加し直さない。

既存チェックリストの全体像は `export` で読む。未処理の分布はフィルタで掴む。

```sh
track export --id <note_id>
track tasks --id <note_id> --state TODO,DOING,WAITING --sort priority
track tasks --id <note_id> --overdue
```

## 2. 書く前に明確化する

依頼、既存ノート、関連コードから目的と制約を確かめる。結果や作業範囲を左右する不足だけをユーザーに尋ね、判明済みの内容と未決事項は分けて記録する。通常の実装方法は既存の規約に沿って判断し、他の着手可能な項目は進める。

## 3. サイズを分ける

各未チェック項目を S/M/L のいずれかに置く。目安は所要セッション数であり、ファイル数ではない。

- S は 1セッションで終わるもの。文言が具体的で、変更箇所が局所的で、検証方法が明らかなもの。
- M は設計判断が残るもの。アプローチの選択肢がある、壊れ得る範囲が広い、事前に合意したい点があるもの。
- L はそのままでは着手できないもの。複数の独立した作業を含み、段階を踏まないと終わらないもの。

サイズは既知の依存関係と未決事項から判断し、新しい事実が分かれば更新する。不確かという理由だけでサイズや承認手続きを増やさない。

## 4. 経路へ回す

サイズごとに行き先が決まる。振り分け自体はノートへ直接書かず、各経路の手順に従う。

- S は [track-project-intake](../track-project-intake/SKILL.md) の手順で `## TODO` または `## Bug` の下に 1行で記録する。依頼者がすぐ作業も望む場合は、記録してから [track-task-runner](../track-task-runner/SKILL.md) へ引き渡す。
- M は未決の判断を intake の `#plan` ノートにまとめ、チェックリスト行から `→ [[<YYYYMMDD> <item summary>]]` でリンクする。既に合意した方針があれば利用し、プランがあることだけを理由に再承認を求めない。
- L は親の `- [ ]` 行の下に段階化した子 `- [ ]` 行を置くか、独立性が高い場合は別ノートへ `track refile` で移す。子項目ごとに着手条件・先行項目・検証方法を記録する。移動先にも `## TODO` / `## Bug` を用意し、親行からリンクして、どのプロジェクトで実行するかを残す。終わった段階は親行へ `(YYYY-MM-DD: <段階> まで完了、残は <何>)` と追記し、全体の進み具合が親だけ読めば分かるようにする。

着手条件が外にある項目は `WAITING` へ置き、待ち先を `(YYYY-MM-DD: <待ち先> 待ち)` と追記する。もうやらないと決めた項目は `CANCELLED` へ置き、理由を一行添える。決して黙って消さない。

## 5. 状態・優先度・期限を付ける

状態の一覧と更新規則は[共通規約](../../references/runtime.md#task-conventions)に従う。振り分けだけで DOING にはしない。状態変更の直前に対象行を読み直し、既知の状態を `--expect` で指定する。単純な開閉だけ `toggle` を使う。

```sh
track task set --id <note_id> --line <N> --state WAITING --expect TODO
track task set --id <note_id> --line <N> --state DOING
track task cycle --id <note_id> --line <N>
track task date --id <note_id> --line <N> --sched 2026-09-10 --due 2026-09-12
```

優先度は本文の `[#A]` で表す。期限は `[sched:]` と `[due:]` を `task date` で付け、今日の焦点は `agenda` と `--overdue` で確認する。

```sh
track agenda --date 2026-09-05
```

## 6. 再インデックスして報告する

検索・リンク・バックリンクが一貫するよう再インデックスする。

```sh
track reindex
```

報告は短く、経路ごとに分ける。S は記録先の見出しと行、M はプランノートのタイトル、L は子項目の数と最初の着手順、WAITING は待ち先、明確化で残った質問があればそれも添える。ノートのタイトルを名指しし、「整理しました」だけでは終わらせない。

## 検証

`export` で新規行が意図した見出しの下にあること、`tasks --sort priority` で優先順位が期待通りであることを確認する。プランノートを作った場合はチェックリスト行からの `[[…]]` が解決されることを `search` で確かめる。

## 安全性

振り分けではノートのタスク行と状態・期限の更新までに留める。push、PR、リリース、依頼外の削除はユーザーの承認範囲に従う。検証が済んでいない項目を DONE へ移さない。
