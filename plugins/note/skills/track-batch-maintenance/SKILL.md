# Track Batch Maintenance

CLI を使う前に[実行環境](../track/references/runtime.md)を読む。状態の保存や再開が必要な場合だけ[バッチ状態の仕様](references/batch-state.md)も読む。

このスキルは指定範囲のノート整理候補と TODO 対応案をまとめる。既定の `proposal` では対象ノートやコードを変更しない。`apply-approved` でも、個別に承認されたノート保守操作だけを対象にし、TODO の実装やコード変更、コミットは別依頼とする。

## 範囲と上限

- 対象 vault と scope を先に確定する。scope が曖昧なら対象集めを始めず確認し、全 vault へ広げない。vault 名が省略された場合は runtime の通常設定を使い、その identity を記録する。
- `proposal` を既定にする。適用には `apply-approved` の指定と、対象・操作・移動先や変更内容が分かる承認が要る。「よさそうなものを進めて」だけでは適用しない。
- 既定上限は、対象30件、作業時間60分、同時実行2件、提示する提案10件。上限は保存済みバッチの再開後も累積し、暗黙にリセットしない。対象は統廃合候補1件または TODO 1行を単位とする。依存元も含めて本文を読むノートは最大30件とし、いずれかの上限に達したら残りを保留・繰越として明示する。
- 60分は目安の予算であり、モデルやツールの呼び出し時間を含む hard wall-clock 保証ではない。利用可能な時計で各呼び出しの直前・直後に経過時間を確認し、最後の10分を照合・状態記録・報告に残す。時間を確認できない場合は上限内と断定せず、後処理の余裕がなければ新しい対象に着手しない。
- 並列2件は、現在の実行環境で許可された独立した読み取り・分析に限る。非対応なら直列で行う。並列数は委譲や外部モデル利用の許可ではなく、外部送信は既存の権限とユーザーの明示許可の範囲に限る。共有ノートへの書き込みは常に直列にする。
- token 残量、reset 時刻、無料モデルの利用可否は、ユーザーまたは実行環境が示す計測値がない限り推定・断定しない。モデルの種類や利用料金は権限、ファイルアクセス、外部送信の許可を変えない。
- バッチ状態・報告だけは、ユーザーが保存先を明示した場合に限り書き込める。strict read-only なら会話内だけで報告し、永続保存・別セッションからの再開はできないと伝える。既定の保存先を作らない。

## 進め方

1. vault、scope、mode、保存先、上限を確定する。不足が結果や許可を左右する場合は確認し、確定した独立対象の検討は続ける。コードが関係する場合は指定されたリポジトリだけを読み、適用前にはそのリポジトリの作業状態と入力版も確認する。
2. 対象種別に必要な skill だけを読む。必要な関連 skill が実行環境で使えなければ、その対象を保留して手順を補わない。検索・本文・依存関係は、実在を確認できる `track` の操作で調べる。コマンド、revision 機能、権限が確認できないときも作らず、その対象を保留する。vault や CLI の環境障害ならバッチ全体を停止して報告する。
3. 候補ごとに対象 ID、入力 revision/hash、判断根拠、依存元とその版を記録する。CLI が提供する版情報がなければ、取得した本文の SHA-256 を使えるローカル手段の有無を確認する。どちらも得られなければ版を `unknown` とし、再開・適用時に変更なしとはみなさない。
4. 証拠と情報保持を確認し、提案を優先順に最大10件示す。各提案には対象、案、根拠、残す情報、依存・リスク、必要な承認を含める。対象ごとの判断を提案・保留・変更不要に分け、上位10件に出さない候補も未処理として分かるようにする。
5. `proposal` では提案と状態を報告して止める。ソースのノート・コード・TODO は変更しない。永続化が明示されている場合でも、書けるのはバッチ状態と報告だけである。
6. `apply-approved` では承認された操作だけを一件ずつ適用する。直前に対象と依存元を読み直し、vault identity・scope・版・承認内容が一致することを確認する。並行する他者の変更を尊重し、一括更新・一括 undo は行わない。各書き込み後に読み直して結果を検証し、状態を更新する。
7. 再開時は[状態仕様](references/batch-state.md)に従い vault identity、scope、入力版、依存元、承認を照合する。適用途中の操作は、版変更による保留を決める前に承認済みの完了状態と現状を照合する。すべて一致すれば再書き込みせず検証済みにできる。これは新たな変更の承認ではない。それ以外で対象か依存元に変化があれば再判定し、古い承認を失効させて新しい承認を得る。試行前状態と完全一致し、元の承認も有効なら未実施操作として一度だけ続けられる。部分適用や結果不明は保留し、自動再試行しない。
8. 判断未決の対象は理由を付けて保留し、独立した対象は続ける。環境障害では停止して正確なエラーと確定済みの進捗を報告する。候補が尽きたら終了し、反復検索や無制限の再試行はしない。

## 振り分け

- 共有変更を巻き戻す全体 undo は行わず、差分を照合できない場合は保留する。journal は書き換えない。
- 複数 report の入口統合には [track-explainer](../track-explainer/SKILL.md) を使い、report 本文を保持する。時点の異なる report を記憶のように上書きしない。
- 完了・期限・WAITING の棚卸しは `track-task-review`、S/M/L・依存・次の提案は `track-task-triage` に従う。該当 skill が実行環境で使えない場合は、その種別を保留し、コマンドや手順を補わない。
- 一般ノートの統廃合は根拠と情報保持を確かめ、提案を基本とする。統合案では canonical 候補、移す内容、出典、失われる情報の有無を示す。削除や履歴の消去を暗黙に含めない。
- TODO の実装・コード編集・テスト・commit はこの skill の範囲外であり、別依頼で `track-task-runner` 等に回す。

## 完了条件と報告

対象上限内の各対象が提案・保留・変更不要・検証済みのいずれかに分類され、根拠と未処理範囲が分かること。`proposal` はソース未変更であることを明記し、`apply-approved` は承認対象と検証結果を個別に報告する。保存先未指定または strict read-only なら会話のみで完了し、永続再開できないことを伝える。token 利用量や hard deadline を計測していない場合は、達成したものとして書かない。
