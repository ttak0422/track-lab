# 日本語レポートの可読性

AI が書いた日本語レポートは、たいてい正確で網羅的で、そして読むのが疲れる。
原因は情報量ではない。次の三つである。

- **均質** — どの段落も同じ長さ、同じ密度、同じ丁寧さで書かれている。読者はどこを読み飛ばしてよいか判断できず、結局すべてを読む羽目になる。
- **無傾斜** — 結論と傍証が同じ扱いで並んでいる。重要度の差が版面に出ていない。
- **未削除** — 調べたことが全部書いてある。人間は書く手間を惜しんで削るが、AI にその制約はない。書ける情報は書いてしまう。

したがって処方も三つになる。読まなくてよい部分を作る（層）、重要度を行数で示す（傾斜）、書いたあとに削る（削除パス）。

## 併用する規範

同じディレクトリ階層の `../track-japanese-tech-writing/SKILL.md` を先に読む。あちらは文と段落のレベル
（一文一行、論証の厳密さ、冗長の排除）を扱う。この規範は**構造と総量**を扱い、そこには踏み込まない。

`../track-cognitive-rhythm-writing/SKILL.md` は読み物向けの緩急の規範である。レポートは読まれないことを
前提とするので、原則として適用しない。最初から通読されるページ（explainer など）で使う。

対象の違いに注意する。読み物は最初から最後まで読まれることを前提に書く。レポートは読まれない。
読者は結論だけ見て閉じるか、自分に関係のある節だけを開く。緩急で読み進めさせるのではなく、
読まずに済ませられる構造を与えるのが目的である。

## 1. 読者と用途を先に一行で決める

書き始める前に、本文の外に一行だけ書く。**誰が、何を決めるか／何を知るために読むか**。

- 「自分が来週この設計を採るか決めるために読む」→ 判断材料と反証だけでよい。調査の経緯は要らない。
- 「半年後の自分が同じ調査を繰り返さないために読む」→ 出典と再現手順が要る。結論の言い換えは要らない。
- 「レビュアが見落としを探すために読む」→ 網羅性と根拠が要る。推奨は一行でよい。

用途が決まると、書かなくてよいものが決まる。これを決めずに書くと、あらゆる読者に備えて全部書くことになる。
それが読み疲れの発生源である。用途は本文には書かない（書くと前置きになる）。

## 2. 層で書く

レポートは四層で構成する。各層は単独で完結し、下の層を読まなくても誤った結論を持ち帰らない。

| 層 | 内容 | 分量 |
| --- | --- | --- |
| L0 結論 | 何が言えるのか。タイトル直下の一行 | 1 行 |
| L1 要約 | これだけで判断できる密度。箇条書きなら 3〜5 項目 | 3〜7 行 |
| L2 本文 | 根拠、手順、反証、トレードオフ | 制限なし |
| L3 付録 | 生ログ、全リスト、生データ、出典 | 制限なし |

守るべきは一点、**上の層は下の層の要約であって、案内ではない**。

- 悪い L1：「本レポートでは A、B、C の三つの観点から比較する。詳細は本文で述べる。」
- 良い L1：「A は B より 3 倍速いが、C の制約下では採れない。採るなら B に D の対策を足す。」

「詳細は後述」「本文で詳しく述べる」と書いた時点で、その層は予告編に落ちている。予告編は読者に
本文を読む義務を課すだけで、何も伝えていない。

L2 で結論を再掲しない。L0 と L1 で言った。末尾に「まとめ」節を置くと、同じ結論が三度現れる。

## 3. 密度に傾斜をつける

- 重要度の差を**行数**で表す。主論点に 20 行、副論点に 3 行。全部を 10 行に揃えない。
- 検討して採らなかった選択肢は、一行ずつの列で足りる。丁寧に葬らない。
- **両論併記をやめる**。判断を求められているなら判断を書き、反対側は反証として一〜二行添える。
  「メリットもデメリットもある」は、判断の放棄を中立に見せかけた形である。
- 判断が本当に割れるなら、**何が分かれば決まるか**を一行で書く。それが読者の次の行動になる。

## 4. 形式を選ぶ

| 形式 | 使う条件 |
| --- | --- |
| 散文 | 因果、条件、理由がある。箇条書きにすると項目間の関係が消える |
| 箇条書き | 順序も因果もない並列の項目が 3〜7 個 |
| 表 | 同じ属性を持つ対象が 3 件以上。比較、対応関係 |

- 箇条書きだけでできた節を作らない。項目間の関係が全部読者の推測に委ねられ、かえって読解が重くなる。
- 箇条書きの入れ子は 2 段まで。3 段になったら構造が間違っている。表か節に変える。
- 同じ形の項目が 5 つ以上並んだら表にする。表は読者に読み飛ばす自由を与える。
- 見出しは 3 階層まで。h4 が要るなら節を切り直す。
- 中身が 3 行しかない節に見出しを立てない。前の節に吸収する。

## 5. 削除パス

書き上げてから、この順で機械的に削る。順序に意味がある。上から削ると下の作業が減る。

1. **前置き** — 冒頭の「本レポートでは〜を扱う」「〜について調査した」を消し、結論から始める。
2. **時系列の痕跡** — 「まず〜を確認した」「次に〜を調べた」（調査の順序）、「当初は〜と考えたが」（理解の変遷）、
   「訂正」「追記」「実は」（前半の誤りを末尾で補う形）を消す。前半が誤っていたなら**前半を直す**。
   行き止まりは順路を捨てて結論一行に畳む（「Y は使えない。理由は〜」）。レポートは調査の記録ではなく、調査の結果である。
   状態を追うノート（プロジェクトノート、watch ノート）はこの限りではない。あちらは履歴が本体である。
3. **重複** — 同じ主張が L1・L2・末尾のまとめに三度ないか。一箇所に減らす。L1 があるなら末尾のまとめ節は消す。
4. **接続の水増し** — 「したがって」「そのため」「また」「さらに」を数える。段落頭の接続詞が 3 段落続いたら 2 つ消す。
5. **評価語** — 「重要」「有効」「最適」「柔軟」「堅牢」「強力」を検索する。数値・条件・機構に置き換えるか、消す。
   「高速」→「30ms」、「柔軟」→「設定ファイルの変更だけで差し替わる」。
6. **保険** — 「一概には言えないが」「場合によっては」「なお、〜には注意が必要である」。
   判断を求められている箇所では判断を書く。不確実性が実在するなら、3 の「密度に傾斜をつける」の規則で
   「何が分かれば決まるか」に変える。
7. **括弧** — 括弧内の補足を、本文に入れるか消すかの二択に振り分ける。重要なら本文、そうでなければ消す。
8. **付録への降格** — 本文中の生ログ、全リスト、網羅的な列挙を L3 に移し、本文には「12 件中 2 件が該当（付録）」だけ残す。
9. **末尾の展望** — 「今後の課題」「さらなる検討が必要である」で閉じる段落を消す。未解決があるなら、具体的な問いの形で一行書く。

1 と 2 と 9 は同じ失敗である。書き手の作業を読者に見せている。

削り終えたら L1 だけを読み直す。それだけで判断できるなら合格。できないなら、L2 から一行 L1 に上げる。

## 6. 改訂パス

レポートの目的は、現時点の結論を記載することである。新しい事実が入ったら、この順で直す
（`track-report` の改訂方式）。

1. **冒頭の結論を先に直す。** 以降の節はそこから従属する。結論が変わらないのに節だけが変わることはない。
2. **主張が変わった節を置換する。** 古い記述を残したまま新しい節を足さない。差分ではなく現状を書く。
3. **陳腐化しうる事実を揃える。** 数値、日付、バージョン、外部の状態（star 数、最終更新日など）。
   本文と脚注の両方を見る。
4. **`## 未決` を整理する。** 解決済みの項目は消す。新しく生じた問いを問いの形で足す。
5. **時系列の痕跡を再点検する。** 改訂自体が痕跡を作る。「当初」「まず」「実は」「追記」「以前は」で
   grep し、ヒットした行が理解の変遷や調査の順路なら消す。

初回執筆では 5 の削除パスを通す。改訂ではこの改訂パスを通し、分量が大きく変わったなら削除パスを
やり直す。

## 7. 日本語の AI 文体 tell

**検出は仮説であって判決ではない。** 同じ文が機構・数値・条件を伴っているなら、tell の形をしていても残す。
「堅牢である」は評価語だが、「再送の冪等キーと dead-letter 打ち切りがあるので堅牢である」は機構を述べており、
削ると情報が減る。リストに当たったら、まず何を根拠にしているかを見る。

**記法**

- 文末のコロン「以下のとおりです：」→「〜は次の三つ。」
- 太字の乱発。一節に一〜二箇所まで。
- スラッシュ並列「設計／実装／検証」→ 読点でつなぐ。
- 見出しや箇条書き頭の絵文字、チェックマーク。
- 言い換えのためのダッシュ（—）。日本語の地の文では括弧か句点に置き換える。

**語彙**

- 「これにより」「〜することで」の連打。
- 中身のない評価語（本質、最適化、価値、活用、推進、〜性の向上）。
- 量産型の比喩（羅針盤、土台、両輪、レシピ、DNA、エンジン、潤滑油）。

**構成**

- 全段落が同じ長さで、どの段落もきれいに閉じる。
- 「結論として」で全体を箱にしまう。
- 各節の末尾が「〜が重要である」で揃う。
- 中立を装う「メリット・デメリット」の対置。

書き換えたら、**書き換えた文にも同じ検査をかける**。冗長な文を削って短い断定に整えると、リズムが良いぶん
tell が残っていても見逃す。これが最大の再侵入経路である。

## 8. 出すまえの点検

1. L1 だけを読んで判断できるか。
2. 最長の節と最短の節の行数比が、重要度の比とおおむね一致しているか。
3. 箇条書きだけで構成された節がないか。入れ子が 3 段になっていないか。
4. 同じ主張が 2 箇所以上に出ていないか。
5. 評価語（重要・有効・最適・柔軟・堅牢）が、機構や数値を伴わずに残っていないか。
6. 節末が全部「〜が重要である」型で閉じていないか。
7. 冒頭が結論から始まっているか。「本レポートでは」で始まっていないか。
8. 時系列の痕跡と後方訂正が残っていないか。`grep -n 'まず\|次に\|当初\|訂正\|追記:\|実は'` で当たりを付け、
   ヒットした行が調査の順路か理解の変遷なら消す。

## track ノートに書くとき

`track-report` の契約（無日期タイトル／冒頭に現時点の結論／節構成は自由／末尾に `## 未決`／出典は
脚注）は、この規範の層とそのまま対応する。タイトル直下の結論が L0+L1、自由な節が L2、
脚注と `## 未決` が L3 にあたる。

- 冒頭の結論は、ここだけで判断できる密度にする。どの節を直したときも、ここを先に直す。
- 節構成は主題の論理に従う。定型の見出しを作らない。
- `## 未決` は削除パス 9 の受け皿である。展望を本文に書かず、問いの形で置く。解決した項目は消す。
- 外部の出典は脚注へ集める。

比較や測定は表と `viewspec`、たどった流れは `mermaid` に寄せる。散文で書かれた比較は、読者が
頭の中で表を再構成することになり、それ自体が読み疲れになる。
